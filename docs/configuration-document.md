# The configuration document

A configuration document is a JSON file that states the desired configuration of an installation
(or of one organisation): organisations and their groups, opening hours, texts, reminders, form
fields, channels, identity providers, API clients, platform settings. It replaces the SQLite
package of ADR 0089 (ADR 0099). It can be read, kept in git, compared between test and
production, written by a pipeline, and applied to an installation of another version: the format
has its own version, independent of the database schema.

The JSON Schema of the format is `docs/configuration-schema/v1.json` (generated by
`python -m app.cli config-schema`); an editor with a JSON Schema plugin completes field names and
flags a typo. The planner is the authority: it also checks everything the admin screens check.

## Shape

```json
{
  "format": "openplanner.config/v1",
  "mode": "merge",
  "scope": "platform",
  "platform": { "settings": { "rate_limit_bookings": "5/hour" } },
  "organisations": [
    {
      "slug": "acme",
      "name": "Acme",
      "settings": { "time_format": "24h" },
      "texts": { "nl": { "message.signoff": "Tot ziens, {group_name}" } },
      "groups": [
        {
          "slug": "helpdesk",
          "name": "Helpdesk",
          "timezone": "Europe/Amsterdam",
          "slot_minutes": 30,
          "min_notice_minutes": 60,
          "horizon_days": 60,
          "phone_mode": "optional",
          "schedule_rules": [
            { "weekday": 0, "opens": "09:00", "closes": "17:00", "capacity": 3 }
          ]
        }
      ]
    }
  ]
}
```

- **Natural keys, never ids.** An organisation is its `slug`, a group its `slug`, an identity
  provider its `key`, an API client its `client_id`, a role its `claim_value`. A document made on
  test therefore applies on production.
- **Partial updates.** A field the document leaves out keeps its value. In a map (`settings`,
  `texts`) `null` removes the entry, which puts the default back.
- **Actions.** Each object may carry `"action": "upsert"` (the default), `create`, `update` or
  `delete`. Deleting an object that is already gone is no change.
- **Modes.** `merge` (the default) leaves what the document does not name. `replace` deletes,
  in every collection the document names, what it does not list; a collection it does not name
  is never touched. Lists that have no key of their own (schedule rules, reminders, form fields)
  are replaced as a whole when named; a form field left out is retired, never deleted.
- **Scope.** `"scope": "platform"` or `{"organisation": "acme"}`. An organisation's document can
  name nothing outside that organisation.
- **Secrets** are `{"sealed": "..."}`: AES-256-GCM under a key derived from a passphrase (at
  least 16 characters) with scrypt, bound to the object and field they belong to. An export
  without secrets leaves them out; applying a document that omits a secret keeps the stored one.
  A secret may also be written by hand as `{"plain": "..."}`: it is read as a secret (validated,
  never printed, sealed under the installation's own key when stored). The host may allow an
  export that writes every secret that way (`CONFIGURATION_PLAINTEXT_EXPORT_ALLOWED`, off by
  default; ADR 0099 point 8a), for a file that is easy to edit and to share: keep it as private as
  the secrets, and wrap it in a tool you trust (an AES zip, `age`, `sops`) before it travels.
- **Files** (logo, fonts, closure images) are inline: media type, SHA-256 and base64 bytes.

## Skills, capacity pools and flows (ADR 0121)

An organisation may carry `skills` (key `code`, `labels`, `archived`) and `capacity_pools`
(counted pools: key `code`, `name`, `guaranteed_skills` as codes, `archived`). A group may carry
`legacy_pool` (the pool that wraps its own staffing: `name`, `guaranteed_skills`, `archived`) and
`flows` (key `code`, `state`, `default_for`, `current_revision`, `draft_revision`) with their
`revisions` (key `revision`, a number). A revision names its counted pool by **code**
(`capacity_pool`) or the legacy pool of its own service by the service's slug (`legacy_pool_of`),
the skills it requires by code (`required_skills`) and, per subject code, the extra skills of that
subject (`subjects`); no id appears anywhere, and neither does `published_by` (a staff id).

- **A pool is found by its code.** The code of a counted pool never changes (migration 0110 gave
  every pool one), so a rename is an ordinary change of `name`. A counted pool whose stored code is
  missing (a row an older image wrote) cannot be addressed: the export is refused with
  `configuration_pool_without_code` naming the pool as `organisation/id`, and a plan or an apply
  leaves that pool alone. Archive it and add it again in the portal, which gives the new one a code.
- **Revisions are history.** An export carries every revision with `published_at` (empty for the
  draft). A document never changes or removes a stored published revision
  (`configuration_revision_published`); a draft may be replaced, and a `replace` document never
  trims the revisions it leaves out.
- **Publishing through a document** is publishing in the portal. A revision that the document
  publishes (a new revision with `published_at`, or a draft that gains one) must be based on the
  revision before it (a skill, pool or subject it names that the one before did not have must be
  there and not archived), have a `published_at` that is not in the future and later than that of
  every revision before it, follow the last revision without a gap, and, as the current one, keep
  the entry paths the flow is the default of. An installation that does not have the flow yet is
  filled in ascending order: each revision is checked against the one before it, and the first one
  may keep what it names although it was archived or removed since.
- **`legacy` is the wrapper and nothing else.** A revision with `legacy: true` is accepted only as
  revision 1 of the flow `appointment` or `direct` of a service, published, opening video and
  completed by `legacy_video_observation`, with no skills, the entry path of its code, drawing on
  the legacy pool of **that service**. Its labels, length and dispatch are a snapshot and may
  differ from the service's settings now. Any other `legacy: true` is refused, as is a draft with
  it. The legacy pool of a service is never named by the flow of another service.
- **Absent is not empty.** A document without these sections (every document of an earlier
  version) leaves the installation's skills, pools and flows as they are. An empty list in a
  `replace` document means none.
- **Archive, not delete.** What a document would delete but that holds history is archived, and
  the plan shows it as `archive`: a skill a person holds or any revision requires, a counted pool
  any revision draws on, a flow with a published revision or a booking. So an **explicit** delete
  of such an object is an archive too, and a `replace` document that leaves it out likewise. Only
  a flow with nothing but a draft, and no booking, is deleted. A flow that was never published
  and that something still refers to is refused with `configuration_draft_flow_in_use`: discard
  its draft in the portal first. An archive needs the reviewed plan hash exactly as a delete does.
  Who holds which skill is not in a document and is never changed by one.
- **Same rules as the screens.** A flow cannot use another organisation's pool or skill, a pool
  cannot stop guaranteeing a skill that a flow not archived still requires from it, two active
  flows cannot be the default of one entry path, a draft cannot name a subject its service does not
  offer, a document cannot set a location, and a flow becomes active only when the readiness
  checklist passes. A default that moves from one flow to another is written releasing before
  gaining, whatever order the document lists the flows in.

## In the portal

The superuser works on *Advanced settings › Configuration package*, an organisation admin (and
the superuser) on *Organisations › organisation › Overview › Configuration*. **Export document**
downloads the scope's configuration, leaving out what the admin could not change themselves;
with *Include secrets* they are sealed under a passphrase typed twice. **Show plan** reads an
uploaded file and lists, per object, the action and the field names (never values), the
refusals, and warnings for deletions, a changed claim value and a replaced Webex Service App
token. **Apply plan** then writes exactly the reviewed document, or nothing. Every one of these
needs a recent login. A group's contact center is `contact_center {kind, routing_value,
attributes}` whatever the platform; for Webex Contact Center `attributes` holds
`business_address` and `channel`.

## Commands on the host

```bash
python -m app.cli config export --format json --no-secrets config.json
python -m app.cli config export --format json --passphrase-file pass.txt config.json
python -m app.cli config export --format json --plain-secrets config.json   # needs the host switch
python -m app.cli config export --format json --organisation acme --no-secrets acme.json
python -m app.cli config plan config.json --passphrase-file pass.txt
python -m app.cli config apply config.json --passphrase-file pass.txt --plan-hash <hash>
```

`plan` prints what would change as lines of action, kind, natural key and field *names*, never a
value, then any refusal, then the plan hash. `apply` plans again inside the write lock and
writes all or nothing; a plan with deletions needs the hash of the plan you reviewed
(`configuration_plan_stale` if the configuration moved on), and a plan above
`CONFIGURATION_APPLY_MAX_CHANGES` is refused. Every applied change is an audit event with its
action, kind and natural key, never a value.

## Setting up a new installation from a file

The aim of an export with secrets is a ready base installation without typing everything again:
the integrations (SMTP, SMS, Webex Service App and its URLs, contact-center connection and
queues per group, login providers, API clients), the organisations and groups, texts and rules.

1. On the source installation: **Export document**, tick *Include secrets*, type a passphrase
   (at least 16 characters) twice. Keep the passphrase apart from the file.
2. On the new installation, one of:
   - the portal: *Advanced settings › Configuration package*, upload the file, type the
     passphrase, **Show plan**, then **Apply plan**;
   - the host: `python -m app.cli config apply config.json --passphrase-file pass.txt`;
   - the installer: `scripts/install.sh --configuration config.json --passphrase-file pass.txt`.
3. No separate tool is needed to open the file. Without the passphrase every secret stays sealed
   and useless; with it the installation opens each one itself and stores it under its own key.

If you would rather encrypt the file yourself (and edit it by hand), the host can allow an
export with the secrets in clear text instead (portal: *Without encryption*;
`config export --plain-secrets`; API: `X-Plain-Secrets: true`). Such a file needs no passphrase
to read in.

A sealed value looks like `{"sealed": "..."}` and the file gets a `seal` block (key
derivation parameters and a check value that tells a wrong passphrase before anything is
planned). A file exported without secrets has neither. The sealed values are meant for
OpenPlanner only. A secret can also be written into a file by hand as `{"plain": "..."}`.

## What a document cannot do

It can do nothing the admin screens refuse: the same validators run, per change the same
permission is asked, objects that bookings, closures or API grants refer to are never deleted,
an archived group stays read-only, and a lower capacity is refused when it creates or worsens a
shortfall. The login-claim mapping is changed on its own screen only.
