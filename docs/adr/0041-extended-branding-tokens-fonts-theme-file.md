# 0041. Extended branding: more tokens, own fonts, header styles and a theme file

Status: accepted (2026-10-27), requested by the product owner. Extends ADR 0020 §4–5 (open
point O5).
Uploads amended by ADR 0092.

## Context

ADR 0020 gave each organisation a display name, one accent colour and one logo, and said that
more branding would be "new tokens in `theme.css`, not new rules". Communications departments
want more: their own typeface, their own text and background colours, a header that looks like
their website, rounder or squarer corners. The product owner asked whether organisations could
simply upload their own stylesheet.

Free CSS was rejected:

- **Accessibility.** CSS can hide labels, remove the focus ring or set grey on grey. Our axe,
  Lighthouse and keyboard tests only see the default style, so a customer stylesheet would
  break WCAG 2.2 AA without CI noticing.
- **Misleading citizens.** `display: none` and `content:` can hide the privacy text or show a
  "booked" message that is not true.
- **Data leaks.** Attribute selectors with `background: url(...)` send typed or pre-filled
  values to another server; `@import` and remote fonts send citizens' IP addresses to third
  parties (GDPR). A CSP cannot tell good CSS from bad.
- **Maintenance.** The HTML structure would become a contract with every customer; any
  template change could break their pages without a failing test.

## Decision

1. **Branding stays a set of validated `--booking-*` tokens.** The organisation's
   `/o/{slug}/theme.css` is generated by us from validated values. No selector, property or
   at-rule written by an organisation ever reaches a browser.
2. **Editable tokens** (domain allow-list in `app/domain/branding.py`, each with a type and
   bounds):
   - colours (`#RRGGBB`): `color-text`, `color-text-muted`, `color-page`, `color-surface`,
     `color-background`, `color-border`, `color-border-strong`, `color-on-accent`, plus the
     accent of ADR 0020;
   - lengths (`px` or `rem`, within bounds): `font-size` (16–20 px), `radius` (0–24 px),
     `radius-small` (0–16 px), `max-width` (640–1440 px);
   - `line-height` (1.4–2.0), `font-weight-heading` (400–900 in steps of 100), `shadow`
     (`none` only, to switch it off);
   - font stacks `font-family` and the new `font-family-heading`: quoted family names and
     generic keywords only, letters, digits, spaces and hyphens, so no `url()` can appear.
   Spacing, target size and the focus colours are not editable: they carry the WCAG
   guarantees (2.5.8, 2.4.7, 2.4.11).
3. **Contrast is checked on save, across tokens.** The domain resolves every token (default or
   override) and checks fixed pairs: text, muted text, accent, error and success against page,
   surface and background at 4.5:1; white-on-accent (`color-on-accent`) at 4.5:1; strong
   borders and the focus ring against their backgrounds at 3:1; text against the focus halo
   at 4.5:1. The admin gets the offending field. Stored branding is not checked against these
   rules again when it is read, so a stricter rule never makes an existing organisation's
   pages fail.
   Dark themes are out of scope: the fixed focus halo needs dark text.
4. **`prefers-contrast: more` wins.** The colour tokens of a theme are wrapped in
   `@media not (prefers-contrast: more)`, so the high-contrast defaults of `site.css` apply
   when a citizen asks for them; the accent stays.
5. **Own fonts** in three roles: text (regular), text bold, heading. WOFF2 only, recognised
   from its bytes, at most 250 kB each, stored in the database and served from
   `/o/{slug}/font/{role}` under the page's own origin (`font-src 'self'` is added to the
   CSP). The theme declares `@font-face` with `font-display: swap` and puts the font first in
   the matching stack. No remote font service, ever. Licensing the font for self-hosting is
   the organisation's responsibility; the screen says so.
6. **Header styles**: `standard` (logo and name, accent line), `accent` (header filled with
   the accent, text in `color-on-accent`) and `logo` (logo only; the logo's `alt` then carries
   the name). Without a logo, `logo` falls back to `standard`. The style is a class on the
   header from a domain enum, styled in `site.css`.
7. **Theme file.** An admin can download the current theme as a `.css` file and upload an
   edited one. The file may contain comments, at most one `:root { ... }` wrapper and
   `--booking-*` declarations from the allow-list; nothing else (no selectors, no at-rules, no
   `!important`, no `url()`), at most 8 kB of UTF-8. A refused file names the first offending
   line. An uploaded file replaces the whole theme: tokens it leaves out return to their
   defaults, the accent included. The same contrast rules apply.
8. **Same rights as ADR 0020.** Everything here needs `branding.manage` (superuser only), a
   fresh login and an audit event naming what changed (`theme`, `header_style`,
   `font.text`, `theme_file`), never the values.
9. **The widget** (ADR 0035) reads the same tokens; a host site sets them on the element or
   inherits its own font.

## Consequences

- Organisations can match their house style closely (colours, typeface, corners, header)
  without our accessibility, privacy or security guarantees depending on their CSS skills.
- Layout changes that tokens cannot express (another page structure, extra blocks) remain
  product work; if several organisations ask for the same, it becomes a new token or variant.
- The admin screen grows: a colours-and-shape form, a fonts card and a theme-file card. The
  manual gets a branding topic.
- New abuse cases in `docs/threat-model.md`: CSS injection through the theme file, a
  disguised font file, oversized uploads; each has a test.
- One migration adds the theme columns and the fonts table; reversible.
