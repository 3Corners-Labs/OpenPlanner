# 0099. Configuration as a JSON document, with a plan and per-object actions

Status: proposed (2026-11-01), requested by the product owner. Not built. Supersedes ADR 0089
points 1 (the package is a SQLite file) and 5 (import only into an installation not in use)
once step 4 is built; ADR 0089 points 2–4 and 6–8 carry over as amended below. Extends ADR
0008 (secrets at rest), ADR 0014 (authorisation) and ADR 0042 (settings classes).

## Context

ADR 0089 made a configuration package a copy of the database with every state table emptied.
That was cheap to build, and it is what the portal, the CLI, the agent API and the installer
offer today. Using it, the product owner found three limits on 2026-11-01, and all three come
from the format:

- **It is tied to one schema revision.** A package imports only into an installation at
  exactly the Alembic revision it was exported from (`configuration_package_version`). Every
  release that adds a migration makes every earlier package useless until ADR 0089 step 5
  (migrate a package forward) is built, and that step would have to run old migrations on a
  file from outside.
- **It is all or nothing.** An import replaces every configuration table, and is refused as
  soon as the installation has one booking, slot or active closure. Changing twelve groups'
  opening hours, adding an organisation, or removing a retired group on a running
  installation cannot be done with it.
- **Nobody can read or write it.** A SQLite file cannot be reviewed in a pull request, kept in
  git, diffed between test and production, or generated by a provisioning pipeline, which was
  the reason ADR 0089 step 3 added the API.

What is wanted is closer to `kubectl apply` or Terraform: a readable document that states the
desired configuration, a *plan* that shows what applying it would change, and per-object
control over create, update and delete, on a fresh installation and on one in use.

## Decision

1. **A configuration document is JSON with its own format version.** The document starts with
   `"format": "openplanner.config/v1"`. The format is part of the product's public contract,
   versioned on its own and independent of the database schema: a migration that adds a
   column with a default does not change it. A change that would break an existing document
   is a new format version (`v2`) with a converter from the previous one in the same PR, and
   the application reads every format version it has ever written. An export always writes
   the newest. The media type is `application/vnd.openplanner.config+json`, the download
   name `openplanner-configuration-<installation>-<date>.json`.
2. **Objects are addressed by natural keys, never by database ids.** An organisation by its
   `slug`, a group by `organisation/slug`, an identity provider by its `key`, an API client by
   its `client_id`, a role by its `claim_value`, a holiday calendar by its `slug`, a log
   destination by its `name`, a platform setting by its registry key, a channel by
   `organisation/channel`, a closure scenario by `organisation[/group]/name`. Where a table
   has no natural key yet (closure scenarios, closure images, fonts and logos), step 1 adds
   one with a unique constraint and a reversible migration. Ids never appear in a document,
   so a document exported from test applies to production.
3. **The document is a tree of aggregates.** `platform` (platform settings, API switch,
   integration credentials, log destinations, custom roles, holiday calendars and their
   days), `organisations[]` (settings, texts, contacts, logos, fonts, origins, holiday
   calendar assignments, channels, identity providers and their keys, closure scenarios and
   images, `groups[]`), each group (settings, texts, form fields, contacts, holiday
   calendars and open days, schedule rules, schedule overrides, reminder rules), and
   `api_clients[]` with their groups. A list without a natural key of its own (schedule
   rules, overrides, reminder rules, form fields, contacts) is a value of its group: when the
   document names it, it replaces that list as a whole. The table registry of ADR 0089 point
   2 stays, and its test now also fails when a configuration table is not reached by a
   mapping of this document.
4. **Each object carries an action.** `upsert` (the default: create or update), `create`
   (refused with `configuration_object_exists` when it exists), `update` (refused with
   `configuration_object_missing` when it does not) and `delete`. Fields of an object are a
   partial update: a field the document leaves out keeps its value; `null` resets a setting to
   its default. A child inherits nothing from its parent's action, except that deleting an
   organisation or group deletes its children.
5. **The document has a mode and a scope.** `"mode": "merge"` (the default) leaves every
   object the document does not name as it is. `"mode": "replace"` deletes, within the
   document's scope, every object of a collection the document names that it does not list;
   a collection the document does not name is never touched. The scope is
   `"scope": "platform"` or `"scope": {"organisation": "<slug>"}`; a document in an
   organisation's scope can name nothing outside that organisation and is refused with
   `configuration_out_of_scope` when it does.
6. **Plan before apply.** Applying a document is two steps with the same code path:
   *plan* reads the document and the current configuration and returns, without writing, the
   list of changes (object, action, changed field names, never values of secrets), the
   refusals with their codes, and a plan hash (SHA-256 over the canonical document and the
   `settings_version` it was computed against). *Apply* computes the plan again and writes
   it in one transaction (`BEGIN IMMEDIATE`, foreign keys checked before the commit), or
   nothing when there is any refusal. In the portal apply always passes the plan hash it
   showed, and is refused with `configuration_plan_stale` when the configuration changed in
   between; on the CLI and the API the hash is optional for a document without deletions
   and required for one with deletions.
7. **Integrity rules live in the domain, per object, not as a lock on the installation.** The
   domain refuses, with a code per object and never the whole installation:
   deleting an organisation, group or closure scenario that a booking, a slot or an active
   closure refers to (`configuration_object_in_use`); lowering a group's capacity below the
   places already booked on an existing slot (`configuration_capacity_below_booked`);
   removing the last enabled login of the platform (`configuration_last_login`); every
   validation rule the corresponding admin form applies (bounds of ADR 0042, the closed field
   catalogue of ADR 0055, the allow-list of placeholders of ADR 0009). A document cannot do
   anything the portal forbids; the plan and the portal share one validation per object.
   Existing slots keep their snapshotted capacity (CLAUDE.md); a changed schedule affects
   slots made after the apply.
8. **Secrets: sealed per value, and optional.** A secret in a document is
   `{"sealed": "<base64>"}`, sealed under a key derived from the passphrase exactly as in ADR
   0089 point 3 (scrypt N 2¹⁶, r 8, p 1, the salt and a verifier in the document's header),
   with the object's natural key and field as associated data, so a sealed value cannot be
   moved to another object. An export is made either *with secrets* (a passphrase is
   required, at least 16 characters) or *without secrets* (no passphrase, every secret field
   left out). On apply, a secret field the document leaves out keeps the installation's
   value; it is never cleared by omission. A document without secrets may therefore be kept
   in git and applied for bulk changes without a passphrase. API client secrets travel as
   their stored hash, sealed like a secret; the clear secret exists nowhere to export. The
   login values of ADR 0089 point 4 travel in the header, sealed, only in an export with
   secrets; the bootstrap keys never travel.
9. **Binary content is inline.** Logos, fonts and closure images are base64 with their
   SHA-256 and media type, validated on apply by the structure checks of ADR 0092, so a
   document stays one file. The size limit of ADR 0089 (`configuration_package_max_mb`)
   applies to the document.
10. **Strict parsing, a published schema.** Unknown fields are refused
    (`configuration_unknown_field`, with the JSON path), so a typo is never a silent no-op.
    The JSON Schema of every format version is generated by
    `python -m app.cli config-schema` into `docs/configuration-schema/v1.json`; CI fails when
    it differs from the code, as for `docs/settings.md`. The document types and the planner
    are pure Python in `app/domain/configuration_document.py`; JSON parsing and the mapping
    to tables are an adapter behind the port `ConfigurationTransfer`, which gets `export`,
    `plan` and `apply` in place of the SQLite methods.
11. **Rights come from the matrix, per change.** The route declares one permission: an
    export or apply in the platform scope `settings.platform.manage`, one in an
    organisation's scope `settings.organisation.manage` for that organisation. Every change
    in the plan is then checked against the permission that the admin screen of that object
    requires to edit it (for example `integrations.manage` for a channel secret); a change
    the actor may not make is a refusal in the plan, not a silent skip. An export leaves out
    the objects the actor may not view and the secrets the actor may not manage. An apply
    with deletions or secrets, and every export with secrets, needs a recent login, as now.
    No new permission. The agent API scope `configuration:transfer` (ADR 0089 point 7) stays
    platform-wide and is checked the same way.
12. **Audit per change.** Every applied change is an audit event under the permission that
    allowed it, with the detail `configuration.apply:<plan hash>` and the object's natural
    key and action, never a value. A plan is not audited; an export is, as now, with its
    scope and whether it held secrets. `settings_version` moves on once per apply.
13. **Where it lives.** The block *Configuration package* on platform → *Advanced settings*
    (ADR 0089 point 6) becomes *Configuration*: export (scope, with or without secrets),
    and import as upload → plan shown as a table → apply. The organisation's own export and
    apply sit on organisation → *Overview* → a sub-tab *Configuration*, next to *Login*
    (ADR 0083 step 2): it is the organisation's configuration as a whole, not one topic of
    it. No new section, top-level entry or tab. On the host:
    `python -m app.cli config export|plan|apply|env` with `--passphrase-file` as now. Over
    the API: `GET /api/agent/v1/configuration` (export), `POST …/configuration/plan` and
    `POST …/configuration/apply`; the `PUT` of ADR 0089 step 3 stays as `apply` with
    `"mode": "replace"` in the platform scope until it is removed in a later breaking-change
    ADR for `/api/v1`. The installer's `--configuration FILE` applies a document to the
    fresh installation.
14. **The SQLite package is retired after a release that reads both.** Step 4 removes the
    SQLite export; import of a SQLite package stays for one minor release, converted on read
    to a `replace` document in the platform scope, and is then removed with ADR 0089 step 5
    dropped. A package exported before this ADR keeps working within that one release.

## Settings

| Key | Class | Default | Bounds | Permission | Note |
|---|---|---|---|---|---|
| `configuration_package_max_mb` | C platform | 64 | 1–512 | `settings.platform.manage` | unchanged from ADR 0089; now the largest document accepted |
| `configuration_apply_max_changes` | C platform | 500 | 1–10000 | `settings.platform.manage` | an apply whose plan has more changes is refused (`configuration_too_many_changes`); a guard against a mistaken `replace` document |

**Fixed on purpose:** the passphrase length (16), the scrypt parameters, the salt size and
the associated data of a sealed value (crypto parameters, ADR 0008); the format versions and
their schemas (a public contract, changed only by a new version); the canonical form hashed
for the plan hash; the integrity rules of point 7 (protections, never switched off from the
portal); the requirement of a plan hash for deletions in the portal.

## Consequences

- A document is reviewable: an installation's configuration can live in git without secrets,
  and a change to it can be a pull request with a plan attached.
- Upgrades no longer invalidate exports. The price is a hand-written mapping per aggregate,
  which ADR 0089 avoided on purpose; the registry test and the generated schema keep it from
  drifting, and a new configuration table now needs its mapping in the same PR.
- Imports into a running installation become possible, so the integrity rules of point 7
  carry the weight the "not in use" lock carried. Every abuse case there gets a test, and
  `docs/threat-model.md` gets the flows *configuration plan* and *configuration apply*
  (tampered document, replayed sealed value on another object, a `replace` document that
  deletes too much, an organisation document that names another organisation).
- `docs/dataflow.md` changes the package from a file to a document; a document without
  secrets holds no secret and no personal data (configuration tables name staff only as a
  group's video host address, as ADR 0089 says).
- The block of ADR 0089 on *Advanced settings* and its manual topic change; the organisation
  overview gets a sub-tab, and `docs/admin-map.md` is regenerated.
- No new dependency: JSON and hashing from the standard library, Pydantic for parsing in the
  adapter, `cryptography` for scrypt and AES-GCM.
