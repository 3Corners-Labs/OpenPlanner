# 0042. Settings layers: code default, admin portal, environment lock

Status: accepted (2026-10-28), requested and accepted by the product owner. Refines ADR 0008 (which
secrets stay in the environment) and the CLAUDE.md stack rule "Settings: `pydantic-settings`
from env only". Builds on ADR 0014/0039 (permissions), ADR 0015 (fresh login), ADR 0031
(audit), ADR 0033 (manual) and ADR 0032 (contact-center connection per organisation). Partly built; see `docs/adr-status.md` for what is built.

## Context

`app/config.py` reads about 55 settings, all from the environment. That made sense for a
skeleton, but it now gets in the way of the product goal that a superuser can run the
service without help from whoever operates the server:

- **Self-reliance.** Changing a retention period, a rate limit, the clock format or the
  sender address means editing `.env` on the host and restarting both containers. Most
  superusers have no shell access, and they shouldn't need it.
- **Visibility.** Nobody in the portal can see what is configured. Support starts with
  "please send me your `.env`", which is exactly what we do not want copied around.
- **Wrong level.** `TIME_FORMAT` and `ADMIN_TIMEZONE` are properties of an organisation, but
  they are set once for the whole installation.
- **Integration secrets in two places.** ADR 0008 moved SMTP and SMS secrets per
  organisation into the database, but the Webex Service App, the WxCC host, the webhook
  secrets and the SMTP fallback still live in the environment.
- **Bootstrap friction.** A fresh production install needs three random keys typed into an
  env file by hand. Docker and Kubernetes secrets (files under `/run/secrets`) are not
  supported.

Some settings really do belong outside the application. A key cannot be stored in the
database it encrypts. The login settings cannot be edited behind the login they configure.
Kill switches must stay out of reach of a hijacked superuser account. Settings that depend on
DNS, the proxy or the container healthcheck belong to the operator. The decision below
separates these cases instead of treating "env" as a single category.

## Decision

### 1. Four classes, each with one home

Every setting belongs to exactly one class:

| Class | Home | Who changes it | Why there |
|---|---|---|---|
| **A. Bootstrap** | environment (or `_FILE`) only | operator | Needed before the database or the login works; or a key that protects the database itself. |
| **B. Deployment** | environment only | operator | Tied to the host, DNS, proxy, image or container healthcheck; or a kill switch that must stay out of the portal. |
| **C. Platform** | database, screen *Advanced settings* | superuser | Behaviour of the whole installation that a superuser can reason about. The environment may **lock** it. |
| **D. Organisation** | database, organisation settings | org admin (own org) / superuser | Differs per organisation. Class C supplies the default for new organisations. |

Class A and B variables are never shown with their value in the portal. Class C and D values
are shown, except secrets (write-only, ADR 0008).

### 2. Precedence: default → portal → environment lock

For a class C or D setting, the effective value is resolved in this order:

1. **Code default**, from the registry (§3).
2. **Portal value**, if a superuser (C) or org admin (D) has set one.
3. **Environment lock.** If the environment variable is set, it wins. The portal then shows
   the setting read-only, with the message "locked by the server operator" and the variable's
   name.

The environment therefore becomes optional for everything outside A and B. An operator who
manages configuration as code can lock what they want. An installation that wants
self-reliance leaves those variables unset.

Class D has one more step: the organisation value overrides the platform default from class
C. Env locks apply to the platform default, not to individual organisations.

### 3. One settings registry

`app/domain/settings_registry.py` (pure domain, no framework imports) declares every setting
once:

- `key` (the env name in lower case), `kind` (int, float, bool, enum, string, URL, rate,
  secret), `default`, `bounds` or allowed values, `class_` (A–D), `secret`, `lockable`;
- `apply`: `live` or `restart`. Class C and D are always `live` (§6);
- `permission`: one of the matrix (§5);
- the i18n keys of the label and hint, and the manual topic (ADR 0033).

From that one source:

- the *Advanced settings* form and the organisation form are rendered, grouped by topic;
- `app/config.py` is checked: a test fails if a `Settings` field has no registry entry or the
  default differs;
- `docs/settings.md` is generated by `python -m app.cli settings-doc`, the same way as
  `docs/authorization.md`, and CI fails when it differs;
- `.env.example` is checked: every class A and B variable is listed and no class C variable
  is listed as required.

### 4. Storage

- Non-secret class C values go in a new table `platform_settings` (`key`, JSON `value`,
  `updated_at`). Class D values go on `organisations` or in a new table
  `organisation_settings` with the same shape.
- Secret class C values (the Webex client secret and refresh token, webhook secrets, the
  SMTP fallback password, the update token) go in the existing `integration_credentials`
  table, sealed under `SETTINGS_ENCRYPTION_KEY` (ADR 0008).
- A single `settings_version` counter goes up with every change (§6).
- Domain validation runs on save, with the registry's bounds and the same cross-field rules
  as `config.py` today (critical storage below low; an SMTP login needs TLS). An invalid
  value is never stored.

### 5. Rights, fresh login, audit

- New permissions in the matrix (ADR 0014; adjustable within the bounds of ADR 0039):
  `settings.platform.view` and `settings.platform.manage`, held by superuser only; and
  `settings.organisation.manage`, held by org admin (own organisation) and superuser.
  The read-only auditor role of ADR 0039 gets `settings.platform.view`.
- Every change needs a fresh login (ADR 0015) and writes an audit event with the key, the old
  value and the new value. For a secret it records only `set` or `cleared`. Refusals are
  audited too.
- Settings that can lock everyone out (§8) have a separate permission,
  `settings.login.manage`, so that ADR 0039 can never hand it to anyone other than the
  superuser.

### 6. Changes apply without a restart

- Web and worker keep the resolved settings in memory and reload them when
  `settings_version` changes. The web container checks at most every 10 seconds; the worker
  checks once per loop.
- Rate limits are passed to `slowapi` as callables, so a new limit applies to the next
  request.
- `LOG_LEVEL` changed in the portal always has an expiry, at most 24 hours, after which it
  falls back to the default. The PII masking of `app/logging.py` applies at every level.

### 7. Security floors for class C

The portal can make the service stricter freely, but looser only up to a hard ceiling in
code. Switching a protection off is not a class C action.

| Setting | Default | Portal bounds | Stays in the environment |
|---|---|---|---|
| `admin_session_hours` | 8 | 1–8 | — |
| `admin_reauth_minutes` | 60 | 5–60 | — |
| `rate_limit_bookings` | 10/hour | 1–30 per hour | `RATE_LIMIT_ENABLED` (off switch) |
| `rate_limit_reads` | 60/minute | 10–300 per minute | idem |
| `rate_limit_agent_tokens` | 10/minute | 1–30 per minute | `AGENT_API_ENABLED` (routes exist) |
| `rate_limit_agent_calls` | 120/minute | 10–600 per minute | idem |
| `system_event_retention_days` | 90 | 30–3650 | — |
| `log_level` | INFO | any, with expiry ≤ 24 h | — |

The CLAUDE.md security baseline (10 bookings/IP/hour, 60 reads/IP/minute) becomes the
default. The ceilings exist for real cases, such as many citizens behind one municipal NAT
address.

### 8. Login settings: changeable, but never a lockout

The OIDC claim names and role values (`oidc_role_claim`, `oidc_organisation_claim`,
`oidc_group_claim`, `oidc_role_*`) are class C because they depend on how the IdP is
configured (open decision O3), and IdP changes shouldn't need a redeploy. Three rules apply:

1. **Saved only after a dry run.** The new mapping is applied to the ID-token claims of the
   superuser's own fresh login. If that login would not resolve to superuser, the change is
   refused.
2. **Lockable.** As with every class C setting, the environment can lock it.
3. **Recoverable from the host** via the CLI in §10, never via a login bypass.
4. **Diagnosable without the portal.** The dry run cannot catch a change on the IdP's side
   (a renamed claim or role). When a login is refused because the mapping finds no role,
   the log records which configured claim was missing and the *names* of the claims that
   were present, never their values. `app.cli oidc-check` (§10) checks the configuration
   without a login. The operator then fixes it with an env lock or `settings reset`.

`OIDC_DISCOVERY_URL`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` and `OIDC_SCOPES` stay in
class A.

**When the IdP is down**, nobody can log in to the admin portal. Citizens are not affected:
they never log in, so booking, reminders, dispatch and the PII purge carry on. The admin
tasks that cannot wait for the IdP to come back get a command in the host CLI (§10). Today
that is only the emergency closure of ADR 0024. Decided by the product owner on 2026-10-28.

Rejected, because each adds a way in that can be abused:

- *A fallback IdP switched on from the environment for a limited time.* Whoever controls
  that IdP, or can set the variable, becomes superuser.
- *A local break-glass account* (password with TOTP or WebAuthn), as Keycloak and GitLab
  offer. This is the login bypass CLAUDE.md rules out.

### 9. Bootstrap: `init` and `_FILE`

- **`python -m app.cli init [--out PATH]`** generates `SETTINGS_ENCRYPTION_KEY`,
  `MANAGEMENT_TOKEN_KEY` and `SESSION_SECRET` (48 random bytes each, `secrets.token_urlsafe`)
  and writes them to `secrets.env` (default `./secrets/secrets.env`, mode `0600`, directory
  in `.gitignore`).
  - It refuses to overwrite an existing file: a new settings key makes every stored secret
    unreadable.
  - It prints the remaining class A and B variables to fill in, without values, and reminds
    the operator to keep a copy of the keys apart from the database backup.
  - Production never generates keys silently at start-up. A key on the same volume as the
    database would undo encryption at rest, and the backup would contain both. The
    development behaviour in `app/keys.py` stays as it is.
- **`_FILE` for every secret in class A and B.** For a secret variable `X`, `X_FILE` names a
  file whose contents (without the trailing newline) are the value, so Docker secrets,
  Kubernetes secrets and secret-store sidecars work without an env file.
  - If both `X` and `X_FILE` are set, start-up is refused.
  - A missing or empty file is refused.
  - A file readable by others is accepted with a warning in the log (name only).
  - This is implemented as an extra `pydantic-settings` source, so no new dependency.
  - Alternative considered: `pydantic-settings`' `secrets_dir`. It was rejected because it
    looks names up implicitly and gives no clear error when a secret is missing.

### 10. Break-glass CLI on the host

`python -m app.cli settings` (run with `docker compose exec web ...`). Access to the host is
the authorisation here, as it already is for backups and updates.

- `settings list`: every setting with its class, its source (default, portal, env, file) and
  whether it is locked. Secrets show only `set` or `not set`.
- `settings show KEY`: the same for one setting.
- `settings reset KEY` or `settings reset --all-class-c`: deletes the portal value, so the
  default or env value applies again.
- `settings set KEY VALUE`: non-secret class C and D only, validated against the registry
  bounds. Secrets are never set or printed by the CLI.
- `oidc-check`: fetches the discovery document and the signing keys, checks the algorithms
  and the redirect URL, and prints the effective claim mapping with its source. It never
  starts a login and prints no secrets.
- `closure start (--group SLUG | --organisation SLUG) --notice-nl TEXT --notice-en TEXT
  [--end ISO]` and `closure lift (--group SLUG | --organisation SLUG)`: the emergency
  closure of ADR 0024 for an IdP outage, with the same domain rules, mails and audit as in
  the portal. Everything else (moving, reinstating, cancelling) waits for the portal.

Every command that changes something writes an audit event with actor `system:cli`. The CLI
can never create users, grant roles or start a session. CLAUDE.md's "no login bypass or role
switcher, ever" is unchanged.

### 11. System status screen

*Advanced settings* opens with a read-only overview for `settings.platform.view`:

- each class A and B variable with `set` / `not set` and its source (env or file), never the
  value;
- the ones that are wrong for production (e.g. a non-https `PUBLIC_BASE_URL`) flagged in the
  same words as the start-up check;
- each class C setting with its effective value and source, and a lock icon when the
  environment locks it.

Support can then ask for a screenshot instead of a `.env`.

### 12. Taking over a value from the environment

For an existing installation, a locked class C setting has an action *Manage this here from
now on*.

- For a non-secret setting, it copies the current env value into the portal.
- For a secret, the server seals the env value into `integration_credentials`. The superuser
  never sees the value.

The screen then tells the operator which variable to remove. The setting stays locked until
it is removed and the containers restart. Both steps are audited.

## Consequences

- A production install only needs classes A and B: nine bootstrap values, of which `init`
  generates three, and the deployment values that already depend on the host.
  `.env.example` shrinks accordingly and lists the class C variables only as optional locks.
- **The settings key matters more.** With more secrets in the database, losing
  `SETTINGS_ENCRYPTION_KEY` costs more. `docs/runbook.md` gets:
  - a mandatory key backup, kept apart from the database backup;
  - a rotation procedure.
  This is tied to open decision O7 (who owns hosting and backups).
- **A compromised superuser can do more harm than today.** That is limited by the floors in
  §7, the kill switches in class B, the env lock, the fresh login and the audit trail.
  `docs/threat-model.md` gets abuse cases for:
  - loosening rate limits;
  - a lockout through the OIDC claim mapping, or a renamed claim on the IdP's side;
  - claim values leaking into the log through the lockout diagnostics;
  - turning `LOG_LEVEL` to DEBUG to fish for data;
  - replacing the SMTP fallback to intercept mail.
  Each abuse case gets a test.
- `docs/dataflow.md` notes that the SMTP fallback and Webex credentials move from the
  environment to the database, encrypted.
- CLAUDE.md, once accepted:
  - "Settings: `pydantic-settings` from env only" becomes "bootstrap and deployment settings
    from env or `_FILE`; platform and organisation settings in the database per ADR 0042,
    lockable from env";
  - the security baseline names its rate limits as defaults with the ceilings of §7.
- New screens need manual topics in `docs/manual/{nl,en}/`: *Advanced settings*, *System
  status* and the organisation settings additions. Every label needs i18n keys in nl and en.
- Migrations: `platform_settings` and `organisation_settings` (or columns on
  `organisations`), plus `settings_version`. All reversible. Existing installations keep
  working unchanged, because every env value they set becomes a lock.
- No new dependency.

## Build order

Each step is its own PR. Each one leaves the service working with the existing `.env`.

1. Registry and the consistency test against `config.py`; `docs/settings.md` generated;
   `settings list/show` in the CLI.
2. `_FILE` support and `app.cli init`; runbook and `.env.example` updated.
3. `platform_settings`, resolution with env lock, reload by `settings_version`; *System
   status* and *Advanced settings* (read-only first); permissions in the matrix.
4. Editable class C, apart from login and secrets: operations, retention, storage, rate limits
   (callables), session lengths, `LOG_LEVEL` with expiry; CLI `set`/`reset`.
5. Class D: `time_format` and `admin_timezone` per organisation.
6. Secrets in class C: SMTP fallback, update token, Webex Service App and WxCC host;
   generated webhook secrets; *Manage this here from now on* (§12). When ADR 0032 is built,
   the Webex/WxCC block moves to the organisation's connection.
7. OIDC claim and role mapping with the dry run of §8.
8. Lockout diagnostics (§8 rule 4), `oidc-check` and the `closure` commands of §10. These
   do not depend on steps 1–7 and can be built at any time.

## Assumptions confirmed

Confirmed by the product owner on 2026-10-28, when the ADR was accepted:

- The bounds in §7 stand as proposed.
- **An environment lock outside the portal bounds is accepted**, so an existing `.env` keeps
  working (e.g. `SYSTEM_EVENT_RETENTION_DAYS=7`, while the portal accepts 30–3650). It is
  flagged "outside portal bounds" by `settings list` and on *System status*. The bounds in
  `app/config.py` stay what the environment may set; the registry holds the portal bounds.
- The C/D split of the inventory stands: only `time_format` and `admin_timezone` are class D;
  the Webex/WxCC block stays class C until ADR 0032 is built. `OIDC_ROLE_AUDITOR` joins the
  login mapping (class C, `settings.login.manage`).
- The permission names of §5 stand. They are added in step 3 to the matrix as it is on `main`
  then; `settings.login.manage` is one of the permissions ADR 0039 can never grant to another
  role.

## Settings

This ADR adds no setting; it classifies every existing one. The classification is
`app/domain/settings_registry.py`, published as `docs/settings.md`.
